§02

What they're running

The jobs collection auto‑deletes a document once that job's end date passes (a TTL index on expire_at) — so it only ever holds currently‑live jobs, never history. runs has no such TTL and keeps every run ever executed, but doesn't store the docker image. So every run below is first classified by keyword‑matching its jobid (researchers name jobs descriptively, e.g. ping‑wroughton) — full coverage, but a guess. The two biggest hits are then confirmed for real in §03 by pulling the actual image.

12,081 runs · 73.6% Don't match any keyword rule. Most of this is a handful of very active, idiosyncratically‑named pipelines — not noise. See §03 and §04: two of the largest are now identified, a large Osnabrück cluster and a one‑off “solar storm” campaign are not yet.

§03

Verified pipelines

No Docker daemon was used or needed. Each image below was pulled straight from its registry's HTTP API — an auth token from auth.docker.io / ghcr.io, the manifest and layer blobs from there — and the layers were untarred to read the entrypoint and source directly.

Ping probe

Template, not live leoscopetestbed/ping:v1

The testbed's one predefined onboarding template. A small Python wrapper around the system ping binary — target, count, interval, deadline and packet size all come from the job's YAML params — parsing packet loss and RTT min/avg/max/mdev into JSON + CSV.

Not represented in any currently‑live job at snapshot time; it exists as a one‑click starting point for new researchers rather than a running pipeline today.

# entrypoint
python3 /app/runner.py
# resolved shell command
ping -c 60 -i 1 -w 60 1.1.1.1

TUM combined suite

Confirmed · live hendrikcech/leotest

The single biggest driver of current activity. A config‑driven Python harness (python3 -m leotest) that, per run, randomly executes a mix of three runners against a Technical University of Munich server:

ping — ICMP latency · stltrace — a custom client/server one‑way‑delay prober (uplink & downlink) · ccmeas — throughput/congestion‑control test driving iperf3 + irtt through a set of testcases over a WireGuard tunnel.

§04

Open threads

Of the 2,101 distinct job names ever scheduled, only 7 still had a live, resolvable docker image at snapshot time — everything else had already aged out of jobs by the time this audit ran. These clusters are large enough to matter but still unidentified:

  • Osnabrück cluster — 2,875 runs across dozens of job names (measurement_osna: 1,039, all historical · osna_series: 852, all in the past 6 months · leo‑measurment‑osnabrueck: 169 · plus a long tail). No surviving image for any of them.
  • A one‑off “solar storm” campaign — 56 single‑run jobs named solar-storm-october-{ping,iperf}-osna-NN (280 runs) plus a non-storm-* control set (30 runs), all historical. Reads like a coordinated ping/iperf correlation study against geomagnetic activity, run from Osnabrück.
  • 56 final‑step‑test‑N jobs (57 runs, all historical) — looks like coursework or a capstone project; low priority.

Suggested next steps: ask the Osnabrück group directly; going forward, stamp the resolved docker image onto each runs document at execution time so history survives the jobs TTL; for older runs specifically, each still has a blob_url pointing at its archived Azure Blob artifact zip (which contains the original experiment-config.yaml) — recoverable with a scoped, short‑lived read‑only SAS token, not attempted here.

Methodology: institution/country parsed from each user's free‑text team field (keyword match, email‑domain TLD fallback, manually reviewed).
